# E1-S4: Transactional audit service with append-only storage

- **ID:** E1-S4
- **Epic:** E1 - Foundation, Policy and Persistence
- **Layer:** Service
- **Slice:** 1
- **Group:** C
- **depends_on:** E1-S3

## Description

Implement the audit service that writes AuditEvent records in the same database transaction as the state transition it describes, including model, prompt, rule-set and correlation traceability and latency and token data. The audit table is append-only at the database role level. Audit failure must prevent a state transition (BRD 10.5, 13.1 row 15) and must never be silently ignored for non-state-changing AI activity.

## Acceptance Criteria

1. An AuditEvent contains timestamp from the injected Clock, account reference, capability, provider, model id, prompt version, PolicyRuleSet version, correlation id, provider latency, tool-call duration, end-to-end interaction duration, token usage where available, redacted input reference, AI output, tool calls, rule results, human override and final action fields
2. The application database role cannot UPDATE or DELETE audit rows: attempted UPDATE and DELETE raise a permission error
3. When the audit insert fails, the accompanying state transition is rolled back and no transition row persists
4. Secrets and prohibited identifiers are redacted before an audit event is stored: an input containing an API key pattern is stored as [REDACTED]
5. When audit persistence fails for a non-state-changing activity the audit service raises AuditUnavailable, callers cannot report the activity as audited, and an operational failure log entry without customer data is written where possible
