# E5-S4: READ and PROPOSE tool contracts with idempotency and call cap

- **ID:** E5-S4
- **Epic:** E5 - AI Orchestration Foundation
- **Layer:** Service
- **Slice:** 1
- **Group:** E
- **depends_on:** E5-S2, E2-S2, E2-S4

## Description

Define explicit tool contracts: READ tools get_account_context and get_eligible_options; PROPOSE tools propose_ptp, flag_hardship, flag_dispute and escalate_to_human. PROPOSE tools create validated proposals only, are idempotent, take only an escalation reason (never a destination) and are capped per turn by validated configuration. Architecture tests keep the LLM away from mutation and decision code.

## Acceptance Criteria

1. The tool registry exposes exactly the six named tools (READ: get_account_context and get_eligible_options; PROPOSE: propose_ptp, flag_hardship, flag_dispute and escalate_to_human) and no tool that mutates balances, payments, arrangements or case decisions directly
2. Each tool validates arguments against a Pydantic schema and an unknown tool name or invalid arguments returns a tool error and never executes
3. Repeating a PROPOSE call with the same idempotency key returns the original result and creates no second proposal
4. escalate_to_human accepts only an EscalationReason enum value and a rationale, any queue, role or reviewer argument is rejected as invalid, and only the routing service decides the destination
5. get_eligible_options returns options only from deterministic services: payable amounts and the PTP date window in Slice 1, with arrangement options added in Slice 2 without changing the tool contract
6. The per-turn tool-call cap is read from validated application configuration (default 5, allowed range 1 to 20) and is not hard-coded
7. Boundary tests with the cap at 5 show that the 4th and 5th calls execute and an attempted 6th call does not execute
8. A tool request not executed because the cap was reached cannot cause any state mutation, and a TOOL_CAP_REACHED audit event is written
9. When the cap is reached the orchestrator returns a safe response or creates an AI_FAILURE_FALLBACK escalation according to policy
10. Architecture tests fail if ai_orchestration or llm_provider imports rules_engine calculation functions directly, or if any LLM-reachable code path calls case decision, dispute resolution, compliance decision, approval or payment-recording operations
