# E6-S6: Officer-recorded Promise-to-Pay (manual workflow)

- **ID:** E6-S6
- **Epic:** E6 - Customer Conversation, Promise-to-Pay and Simulated Payment
- **Layer:** API
- **Slice:** 1
- **Group:** E
- **depends_on:** E2-S2, E2-S4, E2-S5, E3-S1

## Description

Let a Collections Officer record a customer's payment commitment manually (US-005, D-040) as a deterministic fallback so permitted work stays usable when the AI provider is unavailable. It uses the same authorization (COLLECTIONS_OFFICER only, covered by the RBAC matrix), deterministic validation, freshness validation, PolicyRuleSet, idempotency, audit and state-transition rules as the AI-assisted journey and is not a bypass around any guardrail.

## Acceptance Criteria

1. POST /api/ptps lets COLLECTIONS_OFFICER record a customer payment commitment with promised amount, promised date, account, interaction reference and status PENDING, using the same deterministic validation as the chat flow
2. Invalid amounts and dates are rejected with the deterministic reason codes and valid alternatives
3. The manual endpoint works when the LLM provider is unavailable and its module has no dependency on ai_orchestration
4. A duplicate submission with the same idempotency key returns the existing PTP and creates no second record, and a conflicting active PTP or a PTP on a disputed item is rejected with CONFLICTING_ACTIVE_ITEM or DISPUTED_ITEM respectively
5. A stale snapshot is refused by the freshness check, and every recording writes an audit event with the officer persona and PolicyRuleSet version
