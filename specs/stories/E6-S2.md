# E6-S2: Promise-to-Pay creation flow

- **ID:** E6-S2
- **Epic:** E6 - Customer Conversation, Promise-to-Pay and Simulated Payment
- **Layer:** Service
- **Slice:** 1
- **Group:** G
- **depends_on:** E6-S1, E5-S4, E2-S5

## Description

Implement the conversational PTP flow: collect amount and date, validate deterministically, restate service-returned values, require an explicit customer confirmation API action (not an LLM tool decision), revalidate before state change, then create the PTP via the domain service. Handles duplicates and conflicts idempotently (AC-A1..A5, A8).

## Acceptance Criteria

1. A PTP is created only through an explicit customer confirmation API action that references a currently valid deterministic proposal, and the initial statement or an LLM proposal alone never creates a PTP
2. Invalid amount or date input receives the deterministic reason code message and valid alternatives, and creates no PTP
3. Duplicate confirmation submissions with the same idempotency key return the existing PTP and only one PTP row exists
4. A second active PTP on the same account is blocked with CONFLICTING_ACTIVE_ITEM and the customer is offered amend, cancel or an officer
5. The audit trail for the PTP contains input, intent result, proposal, rule validation result, final state and model, prompt and rule-set versions
6. On confirmation the domain service revalidates authorization, policy, snapshot freshness and proposal validity, and a stale or altered proposal is rejected with PROPOSAL_INVALID and creates no PTP
